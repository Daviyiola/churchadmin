# Email attachment and formatting repair

The test-send flow created campaigns without the selected uploads. The actual sending endpoint therefore received no files to attach. Both test and broadcast creation now use `emailCampaignContent`, whose required upload input includes each file's selected attachment/inline mode. Campaign creation verifies every selected upload belongs to the organization; unavailable attachments fail visibly before sending.

The composer previously depended on app CSS, the preview used different list spacing and forced link colors, and the email sent a largely unstyled HTML fragment. A shared renderer now provides explicit email styles for text, paragraphs, lists, emphasis, links, indentation, headings, code, and images. The editor uses the same defaults. All three email editors use a sandboxed, scrollable iframe preview of the outbound HTML document, isolated from the app's CSS. Blank paragraphs and trailing soft breaks retain their vertical space. The preview describes the broadcast footer separately; recipient-specific preference links are added by the managed sender.

Inline images are matched through parsed HTML attributes and rewritten to CID references, with matching attachment IDs. This handles either attribute order and avoids depending on an expiring preview URL in the delivered message. Regular attachments retain their bytes, filename, and MIME type. Missing storage files and malformed file metadata stop the send rather than being silently omitted. Debug logging of image URLs was removed.

Validation: 883 tests in 60 files passed, including 15 new tests covering the actual editor's exported HTML, safe formatting, blank lines, trailing breaks, font/color/alignment preservation, test campaign upload selection, storage failure, tenant-scoped upload validation, outgoing attachment bytes, and CID matching. TypeScript passed. Targeted lint returned zero errors and eight existing warnings in the email pages.

No real email was sent during verification. Browser inspection could not start because its local runtime was unavailable. Inbox rendering on Gmail, Outlook, Apple Mail, and the user's phone therefore remains unverified. Email clients can substitute unavailable fonts or alter colors in dark mode; the document declares a light color scheme and explicit foreground/background colors, but cannot guarantee that clients honor them. Microsoft documents Outlook's message-background changes in [Dark Mode in Outlook](https://support.microsoft.com/en-us/outlook/mail/dark-mode-in-outlook). Attachment payloads follow [Resend's attachment and CID API](https://resend.com/docs/dashboard/emails/attachments).

No database migration is needed for this repair. Changes are local and require application deployment for the hosted site.
